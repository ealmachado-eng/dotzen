# CLAUDE.md

This file orients any Claude instance (Claude Code, Claude Cowork, or chat)
working on **dotzen**. Read this first. Read `/docs/specs/*` before making
architectural decisions. Read `.claude/skills/*` before writing spec DSL
code or engine code — those skills encode hard constraints that are not
obvious from the code alone.

---

## 1. What dotzen is

dotzen is a **governance layer for Terraform infrastructure that is
increasingly generated by AI**. As developers generate HCL via Copilot,
ChatGPT, or agentic coding tools instead of hand-writing it or calling
pre-approved internal modules, there is no guarantee the generated code
respects an organization's security, compliance, or cost policies. dotzen
closes that gap.

The product philosophy is **"Prose as Code."** Governance rules are
written in a fluent, strongly-typed TypeScript DSL that reads like a
policy document, not like software. A security architect who has never
written TypeScript should be able to read `.zen/spec.ts` and understand
exactly what is and is not allowed, and why.

The brand is **dotzen** (working domain: `dotzen.dev` or `dotzen.codes`
as fallback — `zen.codes` was checked and is unavailable). Logo concept:
`.zen`. Tagline: **"Prose as Code."**

## 2. The core architecture (decided)

This is the **only** architecture that should be implemented. Many
alternatives were explored and rejected during design (see
`/docs/specs/00-architecture-decision-record.md` for the reasoning, kept
at the category level so the choice is not re-litigated one language at a
time). Do not reintroduce an alternative engine language — a
native-compiled, JVM/managed-runtime, or dynamically-typed rewrite —
without re-reading that ADR and getting explicit sign-off. The tradeoffs
were already litigated, and the decisive criterion (zero-install
adoption friction) has not changed.

```
┌─────────────────────────────────────────────────────────┐
│  DEVELOPER MACHINE / CI RUNNER                           │
│                                                           │
│  npx @dotzen/dotzen check ./terraform/                    │
│         │                                                 │
│         ▼                                                 │
│  ┌───────────────────────────┐                            │
│  │ Node/TypeScript ENGINE     │  reads .zen/spec.ts (jiti) │
│  │ (the only thing a          │  reads dotzen.json          │
│  │  developer ever touches)   │  evaluates rules            │
│  └──────────┬──────────────────┘                          │
│             │ in-process call (returns parsed JSON)        │
│             ▼                                             │
│  ┌───────────────────────────┐                            │
│  │ hashicorp/hcl → WASM        │  @cdktf/hcl2json (npm dep) │
│  │ (@cdktf/hcl2json)           │  the OFFICIAL parser, one   │
│  │ loaded as data, in-process  │  cross-platform .wasm       │
│  └───────────────────────────┘                            │
└─────────────────────────────────────────────────────────┘
```

**Why this split:**
- **TypeScript is the engine language** because it is the only language
  that lets `npx` deliver a genuinely zero-install experience on every
  developer machine and every CI runner (Node is pre-installed
  essentially everywhere; no other language's package manager achieves
  this — see ADR §4).
- **HCL parsing uses the official `hashicorp/hcl` parser compiled to
  WASM** (`@cdktf/hcl2json`), loaded **in-process** as data — *not* a Go
  subprocess and *not* a per-platform native binary. This is the best of
  both: Terraform-accurate parsing (it *is* the official parser) **and**
  zero platform friction (a single cross-platform `.wasm`, so no
  Gatekeeper/notarization/EDR problems — see §2a). A community pure-TS
  parser (`@evops/hcl-terraform-parser`) was evaluated but only returned
  resource metadata, not attribute bodies, so it was dropped in favor of
  the WASM official parser.
- **Nothing else.** No alternative engine language, no WASM *sandbox* (the
  parser-as-WASM is not a sandbox), no cloud backend for v1. Those are
  v2+ concerns (see §6).

### 2a. Why the parser is WASM, not a native binary (decided)

**This is settled: dotzen uses the official `hashicorp/hcl` parser
compiled to WASM (`@cdktf/hcl2json`), option 2 below.** The section is
kept because the reasoning still matters — if anyone ever proposes
swapping in a native Go binary, this is why not.

A bundled native Go binary distributed via npm would hit macOS Gatekeeper
(quarantined/blocked unsigned on first run), plus Windows
Defender/SmartScreen/EDR friction and a per-OS build matrix. The options,
in order of preference:

1. **(rejected) A pure TypeScript/npm HCL parser.** Zero binary friction,
   but community parsers don't match Terraform's parsing exactly —
   `@evops/hcl-terraform-parser` was tried and only returned resource
   metadata, not attribute bodies, which the engine needs. Dropped.
2. **✅ CHOSEN — `hashicorp/hcl` compiled to WASM, run in-process.** A
   `.wasm` module is loaded as *data*, not executed as an OS process, so
   Gatekeeper, Apple notarization, and Defender/SmartScreen/EDR do not
   apply at all — and it ships as one cross-platform artifact with no
   per-OS build matrix. It is the *official* parser, so parsing matches
   Terraform. Best of both worlds; this is what ships (`@cdktf/hcl2json`).
3. **(not needed) Native binary + Apple Developer ID signing +
   notarization** ($99/yr in release CI). Only if WASM ever proves
   insufficient — no reason to pay this cost today.
4. **(never) Bundle the Go binary + `postinstall` that strips the
   `com.apple.quarantine` xattr.** Some enterprise policies flag tools
   that bypass Gatekeeper this way — a governance tool bypassing OS
   security checks is a bad look. Never ship this.

Full detail (including why WASM beats a native binary) in
`/docs/specs/03-distribution-and-cli.md`.

## 3. The three-tier spec + version model (decided)

1. **The DSL (`.zen/spec.ts`)** — what security architects and platform
   engineers read and write. TypeScript, but disciplined: **no bare
   strings for domain values.** Resource types, ports, effects, tags,
   environments are all `enum`s (regular `enum`, not `const enum` — see
   doc 02's implementation note). A `RuleBuilder` class
   validates completeness at spec-load time. See
   `/docs/specs/02-spec-dsl.md` for the full type-safety layer model —
   **do not implement all six layers described there for v1.** Only
   Layer 1 (const enums) and Layer 6 (builder validation) are required
   for v1. Layers 2–5 (branded types, discriminated unions,
   `ts-pattern` exhaustiveness, Zod runtime validation) are added only
   when real pain justifies them — see that doc's "which layers do I
   actually need" section before adding dependencies.
2. **`dotzen.json`** — the version pin, living in the repository (ideally
   a monorepo — see §4). This is the single source of truth for which
   dotzen version applies. The engine refuses to run if its own version
   does not match `dotzen.json`'s `"version"` field, and prints the
   exact `npx` command to fix it. **Never use `@latest` in any
   automated context** (CI, pre-commit) — only for first-time manual
   evaluation. See `/docs/specs/03-distribution-and-cli.md` §"Version
   pinning" for the enforcement logic and why `@latest` is dangerous for
   a governance tool specifically (silent behavior change, CI/local
   drift, audit trail integrity).
3. **The engine** — invisible to the spec author. Reads the validated
   rule objects, calls the WASM HCL parser (`@cdktf/hcl2json`, in-process),
   evaluates, emits violations with `block` / `warn` / `require_approval`
   effects.

## 4. Monorepo is the recommended deployment topology

dotzen works in a polyrepo, but a **monorepo for Terraform** makes
governance structural rather than voluntary: one `dotzen.json`, one
`spec.ts`, one MR updates everyone simultaneously, one audit trail. If
the target organization already uses polyrepo, dotzen still works per
repo, but flag the monorepo tradeoff explicitly — see
`/docs/specs/04-governance-model.md` §"Monorepo vs polyrepo."

## 5. What "Prose as Code" means operationally

This is not just a tagline — it is a design constraint on every rule
that gets written. A rule is well-formed if a non-technical security
architect can read it and correctly predict what it does. Concretely:

- No bare strings — enums only, so autocomplete guides every choice and
  typos are compile errors, not silent passes.
- No boolean flags with unclear polarity — prefer `mustBeTrue(...)` /
  `denyWhenTrue(...)` over `enabled: true`.
- Every `block`-severity rule should carry a `.message()` and ideally a
  `.rationale()` explaining *why*, not just *what*.
- Prefer many small, named rules over one large conditional rule.

See `/docs/specs/02-spec-dsl.md` for worked examples and the full rule
vocabulary (resource types, conditions, effects).

## 6. Deliberately out of scope for v1 (do not build yet)

These were designed in depth during the project's exploration phase and
are documented for continuity, but **building them now is premature**
and will slow down getting a working v1 in front of real users:

- Deno Deploy cloud backend (central spec registry, violation audit API,
  web dashboard). CI logs + Git history in a monorepo already provide
  an adequate audit trail for v1. See `/docs/specs/05-future-cloud-layer.md`.
- WASM-sandboxed community policy-pack marketplace (AssemblyScript or
  similar). Relevant only once there is a community publishing
  untrusted rule packs — not a v1 problem.
- The separate **AI agent authorization / policy engine** product (its
  own stack, with a fluent-interface DSL for agent delegation chains and
  tool-call scopes). This is a related but distinct product from a
  parallel line of exploration and is **not part of the dotzen
  repository**. Do not conflate the two. If it needs to be built later,
  it gets its own repo and its own CLAUDE.md.
- A future interactive / analytical rule-authoring tier — interesting,
  but not a v1 engine candidate, and it runs asynchronously rather than
  in the fast path. See `/docs/specs/05-future-cloud-layer.md` and the
  ADR for why nothing in this tier belongs in the v1 engine.

A **v0 vertical slice** of `packages/cli/` now exists: the full ROP
pipeline (version → spec-load via jiti → parse via `@cdktf/hcl2json`
WASM → normalize → evaluate → report), twenty-two structurally different
conditions — `denyIngress` / `denyEgress` (SSH/RDP/DB ports vs the
internet on `aws_security_group`, incl. `dynamic` blocks and the
standalone `aws_vpc_security_group_ingress_rule`), `mustHaveTags`
(required tags on any resource), the boolean-attribute trio `mustBeTrue`
/ `mustBeFalse` / `denyWhenTrue` (RDS `storage_encrypted`/`publicly_accessible`,
EBS/EFS `encrypted`, KMS `enable_key_rotation`, DynamoDB/ECR nested
booleans, the four S3 `aws_s3_bucket_public_access_block` flags, ALB
`access_logs`, CloudTrail `is_multi_region_trail`/`enable_log_file_validation`,
IAM password-policy complexity; `mustBeFalse` treats *absent* as a
violation — for attributes whose insecure AWS default is `true`, e.g. EKS
`vpc_config.endpoint_public_access`), `mustBeSet` (attribute must be
present — any value beats absence, e.g. CloudTrail `kms_key_id`), `denyAcl` (public
S3 ACLs, inline or the modern `aws_s3_bucket_acl` resource), `mustEqual`
(e.g. EC2 IMDSv2 `metadata_options.http_tokens` = required — via
nested-block attribute flattening to dotted keys), `mustBeAtLeast` /
`mustBeAtMost` (numeric thresholds, e.g. RDS `backup_retention_period` >= 7,
IAM password length >= 14, IAM `max_password_age` <= 90), and `denyIamWildcard` (flags over-permissive `Allow`
statements in literal-JSON IAM *and* S3 bucket policies — `Action: "*"`,
sharpened to "full administrative access" with `Resource: "*"`, and the
`NotAction` over-broad-grant anti-pattern; `jsonencode(...)`/variable
policies degrade to "could not evaluate"), `listContains` / `listMustInclude` (list
attributes — EKS `public_access_cidrs` = `0.0.0.0/0`, control-plane
logging), `denyValue` (value-in-set — weak ALB `ssl_policy`) and its
allowlist mirror `mustBeOneOf` (value must be in a set — e.g. Cloud SQL
`ssl_mode`; absent counts as a violation),
`denyPlaintextListener` (HTTP/TCP listeners that don't redirect to HTTPS),
`denyPrivilegedContainers` (privileged ECS containers, by parsing
literal-JSON `container_definitions`), `denyLiteral` (a hardcoded
literal where a reference belongs — Secrets Manager `secret_string`, DB
`password`, cluster `master_password`, ElastiCache `auth_token`; a
`var`/`data` reference passes, a literal is the violation), and the two
**presence** conditions — `mustHaveAssociated` (cross-resource: a separate
resource must *reference* this one, e.g. an S3 bucket must have a matching
`aws_s3_bucket_server_side_encryption_configuration` / versioning resource,
a Secrets Manager secret a matching rotation resource; association is by
resource reference, indexed once per run), `mustHaveBlock` (same-resource:
a nested block must be declared, e.g. EKS `encryption_config`) and its
inverse `denyBlockPresence` (a nested block must NOT be declared, e.g. a GCP
instance `network_interface.access_config` = a public IP — detected via
recorded block paths, so even an *empty* block is caught) — across an
AWS vocabulary spanning security groups, RDS (instances + clusters),
Redshift, ElastiCache, S3 (+ACL, +public-access-block, +bucket-policy,
+SSE/versioning), EBS, EFS, KMS, EC2, DynamoDB, ECR, IAM policies, ECS
(services + task definitions), EKS, load balancers (+ listeners), Secrets
Manager, VPC (flow logs + subnet public-IP/IPv6 exposure), CloudTrail
(multi-region / log-file validation / KMS), the IAM account password
policy (CIS AWS §1.8–1.9), and API Gateway (method `authorization` != NONE,
stage access-logging + X-Ray). **The engine is provider-neutral** and now spans
three clouds. **Azure (azurerm)** CIS slice — NSG SSH/RDP ingress (inline
`security_rule` + standalone `azurerm_network_security_rule`), Storage
public-blob/TLS/public-network, MSSQL hardcoded-password/weak-TLS, Key Vault
purge protection, AKS private cluster + local-account-disabled, App Service
HTTPS-only, PostgreSQL/MySQL single-server SSL-enforcement + public-network,
Container Registry admin-user, Cosmos DB public-network, ownership tags, and
RBAC over-permission (`role_definition` `actions:["*"]` via `listContains` —
the analog of AWS `Action:"*"` — and `role_assignment` Owner via `denyValue`;
Azure RBAC needed *no* new parse shape, since `permissions{actions=[…]}`
flattens to a list), plus CIS-L1 breadth: storage/Key-Vault network
default-deny, managed-disk CMK, Key-Vault diagnostic-logging presence
(`mustHaveAssociated` on `azurerm_monitor_diagnostic_setting`), and API
Management legacy-TLS/SSL rejection + public-network.
**GCP (google)** CIS slice — `google_compute_firewall` SSH/RDP from
`0.0.0.0/0`, Storage public-access-prevention + uniform-bucket-level-access,
the public-IAM anti-pattern (`allUsers`/`allAuthenticatedUsers` members) and
primitive roles (`roles/owner`/`editor`) — the GCP analog of an `Action:"*"`
wildcard, via `denyValue` — instance broad `cloud-platform` scope +
`can_ip_forward` + Shielded-VM secure-boot + no-public-IP (`access_config`
via `denyBlockPresence`), GKE legacy-ABAC / private-nodes / network-policy,
KMS `rotation_period`, subnetwork VPC flow logs (`log_config`), bucket
versioning + access logging, and Cloud SQL hardcoded root password + public
IPv4 + `ssl_mode` (a *deep* nested attribute,
`settings.ip_configuration.*`, which the recursive flattener handles). Both non-AWS slices reuse the *same* conditions and pipeline with
**zero new conditions**. Multi-provider vocabulary lives in per-provider
modules (`AwsResource`/`AzureResource`/`GcpResource` +
`*Attribute`, behind the shared `AnyResource` / `AnyAttribute` unions —
members drop the provider prefix, e.g. `AwsResource.SecurityGroup` mirrors
`AzureResource.StorageAccount`). The only provider-specific engine code is
small `normalize` mappers turning Azure NSG rules and GCP firewalls into the
cloud-neutral ingress model. All of this runs with exhaustive condition
dispatch, environment
scoping (`.environment(X)` applies a rule only to resources whose
`environment` tag resolves to X), and the three effects (`block` fails
the build; `warn` and `require_approval` do not, with `require_approval`
emitting the `DOTZEN_REQUIRES_APPROVAL` CI signal per doc 04). Terminal +
JSON output (with TTY/`NO_COLOR`-aware ANSI colors), **multi-root
support** (`terraform` in `dotzen.json` may be an array of roots — e.g.
per-environment `env/{dev,stg,prd}` — each parsed with an *isolated*
var/local scope so they never collide; findings report root-relative
paths). A root may be an object `{ path, environment }` so `.environment(X)`
rule scoping is folder-driven (the declared environment overrides
resource tags) — this is how one spec applies stricter rules to prod than
dev. A `dotzen init` scaffolding command (detects existing Terraform,
including the multi-root/per-environment layout, guessing environment
mappings for recognizable folder names), unit + integration tests, and
the three quality-gate subagents round it out.
It was built to validate the core static-analysis bet (doc 01) and fires
correctly on representative AI-generated HCL. It resolves sole
`${var.x}` / `${local.y}` references (local→var chains, across files) to
definite verdicts and degrades honestly to "could not evaluate" on values
it cannot resolve — including expanding `dynamic` blocks whose `for_each`
resolves to a concrete collection, and flattening nested blocks to dotted
keys at **arbitrary depth** (e.g. GCP `settings.ip_configuration.ssl_mode`).
For **tags** it follows `var`/`local` refs to a map and reads the keys of a
`merge(<literal>, var.tags)` as a *partial* set — keys present are provable,
so `mustHaveTags` passes when all required keys are in the literal portion
and honestly degrades to could-not-evaluate otherwise (never a false
violation, since a `var` arg may add more). It also **follows local
`module {}` calls** (doc 08): each call's inputs are threaded into the
module's `var.*`, so a module's caller-supplied cidrs/tags become concrete
verdicts, reported as `env/prd › modules/rds/main.tf`.
Not built yet (see `docs/ROADMAP.md`):
`jsonencode(...)`-wrapped JSON (IAM policies + ECS `container_definitions`
only parse *literal* JSON today; `jsonencode`/`var` → could-not-evaluate),
`data.aws_iam_policy_document`, `Resource`-only / service-scoped IAM
wildcards (full `Action: "*"` **and** `NotAction`-on-`Allow` are flagged;
`Resource: "*"` alone and `s3:*`-style service wildcards are deliberately
not — to avoid false positives), ECS plaintext env secrets, more
resource/attribute vocabulary, resource-level `count`/`for_each`,
function-wrapped collections (`toset(...)`)/`each.*`, `.tfvars`, and — for
module-following (doc 08) — remote (registry/git) sources, nested modules,
and module `count`/`for_each` (local single-level following IS built). The
`docs/specs` and `.claude` content remains the
authoritative design; treat anything beyond the v0 slice as not yet
written unless you find it.

## 8. Working conventions for this repo

- **Never reintroduce string-typed resource/port/effect values** in the
  spec DSL layer without enum backing. This was a deliberate, hard-won
  design decision (see `/docs/specs/02-spec-dsl.md`).
- **Never default to `@latest`** in any script, CI template, or
  documentation example. Always show `dotzen.json`-driven version
  pinning.
- When adding a new resource type or condition to the vocabulary, update
  it in exactly one place (the enum + builder definitions) and let
  TypeScript's compiler surface every place that needs updating — this
  is the intended workflow, not a limitation to work around.
- Before writing engine code, read the
  `.claude/skills/dotzen-engine-dev/SKILL.md` skill.
- Before writing or editing `.zen/spec.ts` files (in this repo's
  examples, or for a consuming organization), read the
  `.claude/skills/dotzen-spec-authoring/SKILL.md` skill.

## 9. Development workflow: TDD + quality/security gate (decided)

dotzen is built **test-first** and every change passes a standing
quality/security gate. Full detail in
`/docs/specs/07-development-workflow.md`; the non-negotiables:

- **TDD, red → green → refactor.** No production code without a failing
  test first. "A feature" is small — a pipeline stage, a condition
  evaluator, a `Result` combinator each get a test first. See doc 06 for
  why the architecture is trivially testable.
- **The gate runs on every change**, via two surfaces running the *same*
  tools so local and CI never disagree:
  - **Dev-time subagents** (in `.claude/agents/`): `test-runner`,
    `code-quality`, `security-scan`. Launch all three **in parallel**
    after a change; a check that could not run counts as a failure, never
    a silent pass; a feature is not done until all three PASS.
  - **CI** (`.gitlab-ci.yml`, GitLab CI): the non-bypassable gate on
    push/MR. Linux is the guaranteed gate; Windows+macOS parity jobs are
    gated behind `ENABLE_CROSS_OS` (they need GitLab SaaS/self-hosted
    runners for those OSes). Update automation via Renovate
    (`renovate.json`), not Dependabot.
- **Tools** (all dev/CI only — never shipped in the npm package, so a
  native dev tool does not breach the "stay pure-JS" distribution
  boundary): Vitest (+coverage), `tsc --noEmit`, ESLint
  (+eslint-plugin-security), Prettier, Semgrep, gitleaks, npm audit,
  osv-scanner.
- **Definition of Done:** written test-first; all three subagents PASS;
  CI green; any new rule condition/resource type ships its violating +
  passing fixtures.
