# CLAUDE.md

This file orients any Claude instance (Claude Code, Claude Cowork, or chat)
working on **pluvian**. Read this first. Read `/docs/specs/*` before making
architectural decisions. Read `.claude/skills/*` before writing spec DSL
code or engine code — those skills encode hard constraints that are not
obvious from the code alone.

---

## 1. What pluvian is

pluvian is a **governance layer for Terraform infrastructure that is
increasingly generated by AI**. As developers generate HCL via Copilot,
ChatGPT, or agentic coding tools instead of hand-writing it or calling
pre-approved internal modules, there is no guarantee the generated code
respects an organization's security, compliance, or cost policies. pluvian
closes that gap.

The product philosophy is **"Prose as Code."** Governance rules are
written in a fluent, strongly-typed TypeScript DSL that reads like a
policy document, not like software. A security architect who has never
written TypeScript should be able to read `.pluvian/spec.ts` and understand
exactly what is and is not allowed, and why.

The brand is **pluvian** — an [erkos](https://erkos.dev) tool (erkos = Greek
ἔρκος, "enclosure/rampart"; the umbrella brand). The name comes from
*Pluvianus aegyptius*, Herodotus's crocodile bird — the bird that cleans
the crocodile's teeth; the tool cleans the AI's Terraform. The crocodile
is the company mascot. Logo concept: `.pluvian`. Tagline: **"Prose as
Code."**

## 2. The core architecture (decided)

This is the **only** architecture that should be implemented. Many
alternatives were explored and rejected during design (see
`/docs/specs/00-architecture-decision-record.md` for the reasoning, kept
at the category level so the choice is not re-litigated one language at a
time). Do not reintroduce an alternative engine language — a
native-compiled, JVM/managed-runtime, or dynamically-typed rewrite —
without re-reading that ADR and getting explicit sign-off. The tradeoffs
were already litigated, and the decisive criterion (zero-install
adoption friction) has not changed.

```
┌─────────────────────────────────────────────────────────┐
│  DEVELOPER MACHINE / CI RUNNER                           │
│                                                           │
│  npx @erkos/pluvian check ./terraform/                    │
│         │                                                 │
│         ▼                                                 │
│  ┌───────────────────────────┐                            │
│  │ Node/TypeScript ENGINE     │  reads .pluvian/spec.ts (jiti) │
│  │ (the only thing a          │  reads pluvian.json          │
│  │  developer ever touches)   │  evaluates rules            │
│  └──────────┬──────────────────┘                          │
│             │ in-process call (returns parsed JSON)        │
│             ▼                                             │
│  ┌───────────────────────────┐                            │
│  │ hashicorp/hcl → WASM        │  @cdktf/hcl2json (npm dep) │
│  │ (@cdktf/hcl2json)           │  the OFFICIAL parser, one   │
│  │ loaded as data, in-process  │  cross-platform .wasm       │
│  └───────────────────────────┘                            │
└─────────────────────────────────────────────────────────┘
```

**Why this split:**
- **TypeScript is the engine language** because it is the only language
  that lets `npx` deliver a genuinely zero-install experience on every
  developer machine and every CI runner (Node is pre-installed
  essentially everywhere; no other language's package manager achieves
  this — see ADR §4).
- **HCL parsing uses the official `hashicorp/hcl` parser compiled to
  WASM** (`@cdktf/hcl2json`), loaded **in-process** as data — *not* a Go
  subprocess and *not* a per-platform native binary. This is the best of
  both: Terraform-accurate parsing (it *is* the official parser) **and**
  zero platform friction (a single cross-platform `.wasm`, so no
  Gatekeeper/notarization/EDR problems — see §2a). A community pure-TS
  parser (`@evops/hcl-terraform-parser`) was evaluated but only returned
  resource metadata, not attribute bodies, so it was dropped in favor of
  the WASM official parser.
- **Nothing else.** No alternative engine language, no WASM *sandbox* (the
  parser-as-WASM is not a sandbox), no cloud backend for v1. Those are
  v2+ concerns (see §6).

### 2a. Why the parser is WASM, not a native binary (decided)

**This is settled: pluvian uses the official `hashicorp/hcl` parser
compiled to WASM (`@cdktf/hcl2json`), option 2 below.** The section is
kept because the reasoning still matters — if anyone ever proposes
swapping in a native Go binary, this is why not.

A bundled native Go binary distributed via npm would hit macOS Gatekeeper
(quarantined/blocked unsigned on first run), plus Windows
Defender/SmartScreen/EDR friction and a per-OS build matrix. The options,
in order of preference:

1. **(rejected) A pure TypeScript/npm HCL parser.** Zero binary friction,
   but community parsers don't match Terraform's parsing exactly —
   `@evops/hcl-terraform-parser` was tried and only returned resource
   metadata, not attribute bodies, which the engine needs. Dropped.
2. **✅ CHOSEN — `hashicorp/hcl` compiled to WASM, run in-process.** A
   `.wasm` module is loaded as *data*, not executed as an OS process, so
   Gatekeeper, Apple notarization, and Defender/SmartScreen/EDR do not
   apply at all — and it ships as one cross-platform artifact with no
   per-OS build matrix. It is the *official* parser, so parsing matches
   Terraform. Best of both worlds; this is what ships (`@cdktf/hcl2json`).
3. **(not needed) Native binary + Apple Developer ID signing +
   notarization** ($99/yr in release CI). Only if WASM ever proves
   insufficient — no reason to pay this cost today.
4. **(never) Bundle the Go binary + `postinstall` that strips the
   `com.apple.quarantine` xattr.** Some enterprise policies flag tools
   that bypass Gatekeeper this way — a governance tool bypassing OS
   security checks is a bad look. Never ship this.

Full detail (including why WASM beats a native binary) in
`/docs/specs/03-distribution-and-cli.md`.

## 3. The three-tier spec + version model (decided)

1. **The DSL (`.pluvian/spec.ts`)** — what security architects and platform
   engineers read and write. TypeScript, but disciplined: **no bare
   strings for domain values.** Resource types, ports, effects, tags,
   environments are all `enum`s (regular `enum`, not `const enum` — see
   doc 02's implementation note). A `RuleBuilder` class
   validates completeness at spec-load time. See
   `/docs/specs/02-spec-dsl.md` for the full type-safety layer model —
   **do not implement all six layers described there for v1.** Only
   Layer 1 (const enums) and Layer 6 (builder validation) are required
   for v1. Layers 2–5 (branded types, discriminated unions,
   `ts-pattern` exhaustiveness, Zod runtime validation) are added only
   when real pain justifies them — see that doc's "which layers do I
   actually need" section before adding dependencies.
2. **`pluvian.json`** — the version pin, living in the repository (ideally
   a monorepo — see §4). This is the single source of truth for which
   pluvian version applies. The engine refuses to run if its own version
   does not match `pluvian.json`'s `"version"` field, and prints the
   exact `npx` command to fix it. **Never use `@latest` in any
   automated context** (CI, pre-commit) — only for first-time manual
   evaluation. See `/docs/specs/03-distribution-and-cli.md` §"Version
   pinning" for the enforcement logic and why `@latest` is dangerous for
   a governance tool specifically (silent behavior change, CI/local
   drift, audit trail integrity).
3. **The engine** — invisible to the spec author. Reads the validated
   rule objects, calls the WASM HCL parser (`@cdktf/hcl2json`, in-process),
   evaluates, emits violations with `block` / `warn` / `require_approval`
   effects.

## 4. Monorepo is the recommended deployment topology

pluvian works in a polyrepo, but a **monorepo for Terraform** makes
governance structural rather than voluntary: one `pluvian.json`, one
`spec.ts`, one MR updates everyone simultaneously, one audit trail. If
the target organization already uses polyrepo, pluvian still works per
repo, but flag the monorepo tradeoff explicitly — see
`/docs/specs/04-governance-model.md` §"Monorepo vs polyrepo."

## 5. What "Prose as Code" means operationally

This is not just a tagline — it is a design constraint on every rule
that gets written. A rule is well-formed if a non-technical security
architect can read it and correctly predict what it does. Concretely:

- No bare strings — enums only, so autocomplete guides every choice and
  typos are compile errors, not silent passes.
- No boolean flags with unclear polarity — prefer `mustBeTrue(...)` /
  `denyWhenTrue(...)` over `enabled: true`.
- Every `block`-severity rule should carry a `.message()` and ideally a
  `.rationale()` explaining *why*, not just *what*.
- Prefer many small, named rules over one large conditional rule.

See `/docs/specs/02-spec-dsl.md` for worked examples and the full rule
vocabulary (resource types, conditions, effects).

## 6. Deliberately out of scope for v1 (do not build yet)

These were designed in depth during the project's exploration phase and
are documented for continuity, but **building them now is premature**
and will slow down getting a working v1 in front of real users:

- Deno Deploy cloud backend (central spec registry, violation audit API,
  web dashboard). CI logs + Git history in a monorepo already provide
  an adequate audit trail for v1. See `/docs/specs/05-future-cloud-layer.md`.
- WASM-sandboxed community policy-pack marketplace (AssemblyScript or
  similar). Relevant only once there is a community publishing
  untrusted rule packs — not a v1 problem.
- The separate **AI agent authorization / policy engine** product (its
  own stack, with a fluent-interface DSL for agent delegation chains and
  tool-call scopes). This is a related but distinct product from a
  parallel line of exploration and is **not part of the pluvian
  repository**. Do not conflate the two. If it needs to be built later,
  it gets its own repo and its own CLAUDE.md.
- A future interactive / analytical rule-authoring tier — interesting,
  but not a v1 engine candidate, and it runs asynchronously rather than
  in the fast path. See `/docs/specs/05-future-cloud-layer.md` and the
  ADR for why nothing in this tier belongs in the v1 engine.

The engine in `packages/cli/` is shipped (v1.9.x), not a vertical slice:
the full ROP pipeline (version → spec-load via jiti → parse via
`@cdktf/hcl2json` WASM → normalize → evaluate → report) with **42
structurally different conditions** — including the v1.9.26–29 graph-layer
conditions (`denyIfReachable` / `denyIfSharedWith` / `denyIfReachableAttr`)
— across AWS, Azure, and GCP (~3,200 recognized types).

**Authoritative condition catalog** (the inline list that used to live here
was illustrative and rotted between releases; trust these instead):

- `packages/cli/src/spec/rule.ts` — the `Condition` union (source of truth).
- `docs/ROADMAP.md` — backlog + dogfood log with the why behind each fix.
- `packages/cli/CHANGELOG.md` — what shipped when.
- `docs/user/reference/rules/` — auto-generated per-preset/per-resource catalog (`npm run gen-docs`).

The condition families in brief (see the sources above for the full list):

- **Boolean attributes** — `mustBeTrue` / `mustBeFalse` / `denyWhenTrue` / `mustBeSet`.
- **Value matching** — `mustEqual`, `denyValue`, `mustBeOneOf`, `mustBeAtLeast` / `mustBeAtMost`.
- **Lists** — `listContains`, `listMustInclude`.
- **Network exposure** — `denyIngress` / `denyEgress`, `denyAcl`, `denyPlaintextListener`, `denyPublicPrincipal`, `requireSslOnlyPolicy`.
- **IAM** — `denyIamWildcard` (literal-JSON *and* `jsonencode`, incl. `NotAction` over-broad-grant), `denyValue` on Azure RBAC `actions:["*"]` and GCP primitive roles.
- **Secrets** — `denyLiteral` (hardcoded secret), `denyPlaintextEnvSecrets` (ECS env-var name pattern).
- **Containers** — `denyPrivilegedContainers`.
- **Block presence** — `mustHaveBlock` / `denyBlockPresence` (e.g. GCP `access_config` = public IP).
- **Cross-resource association** — `mustHaveAssociated` (S3 ↔ SSE/versioning resource, Secrets Manager ↔ rotation).
- **Topology-aware (graph layer)** — `denyIfReachable` (EFS mount target → public subnet → IGW), `denyIfSharedWith` (no shared SG between public LB and private DB), `denyIfReachableAttr` (bucket's KMS key must be customer-managed).
- **Region / data residency** — `denyNonApprovedRegion`.

All conditions degrade honestly to `couldNotEvaluate` for unresolvable
values (a `var`-supplied CIDR, an opaque `for_each`) — for a governance
tool, a false positive is worse than an honest gap. The pipeline threads
`var`/`local` refs (incl. `merge(...)` tag maps, `dynamic` blocks, nested
module inputs), and **follows local `module {}` calls** (doc 08) so
caller-supplied values become concrete verdicts. Multi-root support:
`terraform` in `pluvian.json` may be an array of roots, each parsed with
isolated var/local scope. A `pluvian init` scaffolding command detects
existing Terraform (incl. multi-root layouts) and writes a version-pinned
`pluvian.json` + `.pluvian/spec.ts`.

Not built yet (see `docs/ROADMAP.md`):
`data.aws_iam_policy_document`, service-scoped IAM wildcards (deliberately
not flagged — to avoid false positives), ECS plaintext env secrets (more
shapes), more resource/attribute vocabulary, resource-level
`count`/`for_each`, function-wrapped collections (`toset(...)`/`each.*`),
`.tfvars`, and — for module-following (doc 08) — remote (registry/git)
sources. The `docs/specs` and `.claude` content remains the authoritative
design; treat anything beyond the shipped slice as not yet written unless
you find it.

## 8. Working conventions for this repo

- **Never reintroduce string-typed resource/port/effect values** in the
  spec DSL layer without enum backing. This was a deliberate, hard-won
  design decision (see `/docs/specs/02-spec-dsl.md`).
- **Never default to `@latest`** in any script, CI template, or
  documentation example. Always show `pluvian.json`-driven version
  pinning.
- When adding a new resource type or condition to the vocabulary, update
  it in exactly one place (the enum + builder definitions) and let
  TypeScript's compiler surface every place that needs updating — this
  is the intended workflow, not a limitation to work around.
- Before writing engine code, read the
  `.claude/skills/pluvian-engine-dev/SKILL.md` skill.
- Before writing or editing `.pluvian/spec.ts` files (in this repo's
  examples, or for a consuming organization), read the
  `.claude/skills/pluvian-spec-authoring/SKILL.md` skill.

## 9. Development workflow: TDD + quality/security gate (decided)

pluvian is built **test-first** and every change passes a standing
quality/security gate. Full detail in
`/docs/specs/07-development-workflow.md`; the non-negotiables:

- **TDD, red → green → refactor.** No production code without a failing
  test first. "A feature" is small — a pipeline stage, a condition
  evaluator, a `Result` combinator each get a test first. See doc 06 for
  why the architecture is trivially testable.
- **The gate runs on every change**, via two surfaces running the *same*
  tools so local and CI never disagree:
  - **Dev-time subagents** (in `.claude/agents/`): `test-runner`,
    `code-quality`, `security-scan`. Launch all three **in parallel**
    after a change; a check that could not run counts as a failure, never
    a silent pass; a feature is not done until all three PASS.
  - **CI** (`.github/workflows/ci.yml`, GitHub Actions): the non-bypassable
    gate on push/PR (Node 24). Update automation via Renovate
    (`renovate.json`), not Dependabot.
- **Tools** (all dev/CI only — never shipped in the npm package, so a
  native dev tool does not breach the "stay pure-JS" distribution
  boundary): Vitest (+coverage), `tsc --noEmit`, ESLint
  (+eslint-plugin-security), Prettier, Semgrep, gitleaks, npm audit,
  osv-scanner.
- **Definition of Done:** written test-first; all three subagents PASS;
  CI green; any new rule condition/resource type ships its violating +
  passing fixtures.
